# The F₂ Algebra — Theory and Use

This document explains the mathematics behind the F₂ algebra
(`internal/f2`), the model the code implements, the guarantees the test
suite actually enforces, and when F₂ is the right tool. It is written for a
compiler engineer deciding which layout algebra fits their problem; the
formal fold-engine model lives in
[`internal/f2/theory.md`](../internal/f2/theory.md), and this document links
to it rather than duplicating it. For the other algebra see
[`doc/subgroupchain.md`](./subgroupchain.md) and the top-level
[README](../README.md).

Prerequisites: familiarity with GPU threading (warps, lanes, memory
transactions) and basic linear algebra (vector spaces, rank, matrices over
small fields). No abstract algebra beyond "field with two elements" is
assumed.

## 1. The math: arithmetic over GF(2)

The field with two elements — F₂, also written GF(2) — has elements `{0, 1}`
with:

| operation | F₂ meaning | bit meaning |
|---|---|---|
| addition `a + b` | XOR | `a ^ b` |
| multiplication `a · b` | AND | `a & b` |
| additive inverse | `a` itself (`a + a = 0`) | negation is free |

The payoff: **bit vectors are F₂ vectors**. An n-bit quantity is an element
of the F₂ vector space F₂ⁿ, and any map that computes each output bit as an
XOR of input bits is a **linear map** — i.e. a matrix over F₂.

Why layouts become linear algebra: every layout decision in the
power-of-2 world is a decision about which input bit lands in which output
bit position:

- a **permutation** of coordinates is a permutation matrix;
- an **XOR swizzle** (`bank ^= lane_bit`) is an involutory matrix
  (M⁻¹ = M, because XOR-ing twice restores the input);
- a **stride** (multiply by 2ᵏ) is a shift — multiplication by the monomial
  xᵏ in the polynomial ring F₂[x]/(xⁿ);
- **bijectivity** of a mapping is exactly matrix rank = n, computed by
  Gaussian elimination in F₂ (`internal/f2/matop.go`).

Questions like "is this mapping bijective?", "how many distinct 32B sectors
does this warp touch?", and "which lane bits decide the bank?" become
**exact rank/nullity computations** with provable answers — not heuristics.

### What "exact" means here

F₂ results are exact in the strong sense: a certified `Score{LineRank,
SectorRank}` counts exactly `2^LineRank` cache lines and `2^SectorRank`
sectors touched by a warp sweep, because the touched set is an affine image
of an F₂ subspace and its cardinality is 2^rank. Nothing is sampled or
estimated. Compare the sub-group chain algebra, whose analyses over
arbitrary (non-power-of-2) factorizations are **conservative**: its passes
may decline a layout they cannot prove safe (false negatives are
acceptable; wrong math is not — see
[`doc/subgroupchain.md`](./subgroupchain.md)).

## 2. The model

The library generates a mapping from **hardware coordinate bits** to a
**final memory offset** in a tile — delivered as a *vector*: one F₂
expression per output offset bit, MSB-first.

Concretely, the user sets up an F₂ interpreter parametrized by symbolic
tile dimensions (M, N) and provides the hardware coordinate vector: named
bit variables (warp bits, lane bits) ordered MSB-first with the CUDA
convention that the **trailing** entries are the per-warp lane bits
(`threadIdx.x` is fastest-varying). The pipeline then composes F₂-linear
maps:

```
hw coordinate bits ──► MapAccess ──► StrideMap ──► (SwizzleMap | M) ──► offset vector
(bit variables         (permutation  (coordinate    (SMEM bank XOR  (one expression
 MSB-first,            of hw basis    space → byte   | GMEM           per offset bit)
 lane bits last)       onto tile      space, × dtype coalescing M)
                       coordinates)   size)
```

Each stage's output is itself a bit vector whose entries are F₂ expressions
over the hw variables, so the composition is computed symbolically — the
final vector is what a code generator interprets into index arithmetic.
Because every expression is folded to a canonical normal form first
(six-rule rewrite engine, see `internal/f2/theory.md`), equal subexpressions
print and emit identically: common-subexpression elimination comes free at
emission time.

### Why the power-of-2 restriction

Bit addressing. The entire model identifies "position k in the tile" with
"bit k of a binary numeral", which is only possible when every extent and
stride is a power of two. Non-power-of-2 strides involve multiplication by
odd constants, and carries make such multiplication non-linear over F₂ —
outside the model, by design. For arbitrary tile factorizations use the
[sub-group chain algebra](./subgroupchain.md).

## 3. Worked example (verified program output)

Problem: tile `[4, 8]` of 4-byte elements, hardware concurrency 4 warps ×
8 lanes (`w` bound 4 → bits w1 w0; `t` bound 8 → bits t2 t1 t0), lane-last
by the trailing-lane convention. The access stage maps the 5-bit hardware
vector onto the row-major `[4, 8]` tile (2 major bits + 3 minor bits) and
shifts into byte space (`× 4B = × 2²`, so the two low byte bits are
constant 0):

```
(((((((w1 * 64) + (w0 * 32)) + (t2 * 16)) + (t1 * 8)) + (t0 * 4)) + (0 * 2)) + (0 * 1))
```

Reading the linear algebra directly off the AST: byte-bit 6 = w1, bit 5 =
w0, bit 4 = t2, bit 3 = t1, bit 2 = t0, bits 1,0 = 0. As a matrix over
basis (w1, w0, t2, t1, t0), the byte-offset map is the 7×5 matrix with a
single 1 in each column at rows 6, 5, 4, 3, 2 — rank 5, hence injective on
the 32-element tile (bijective onto its image, the byte multiples of 4).

Evaluating at every (w, t) — the full 32-point assignment space, exactly
what `pkg/ast`'s reference evaluator computes:

```
  (0,0) ->   0  (0,1) ->   4  (0,2) ->   8  (0,3) ->  12  (0,4) ->  16  (0,5) ->  20  (0,6) ->  24  (0,7) ->  28
  (1,0) ->  32  (1,1) ->  36  (1,2) ->  40  (1,3) ->  44  (1,4) ->  48  (1,5) ->  52  (1,6) ->  56  (1,7) ->  60
  (2,0) ->  64  (2,1) ->  68  (2,2) ->  72  (2,3) ->  76  (2,4) ->  80  (2,5) ->  84  (2,6) ->  88  (2,7) ->  92
  (3,0) ->  96  (3,1) -> 100  (3,2) -> 104  (3,3) -> 108  (3,4) -> 112  (3,5) -> 116  (3,6) -> 120  (3,7) -> 124
```

Per warp (fixed w): 8 lanes × 4B = 32 consecutive bytes — one 32B sector,
one 128B line: perfect coalescing. This is the GMEM stage's answer too: by
the trailing-lane convention the identity permutation is provably optimal,
so `GmemOptimize` returns the same offset with a certified plan
(`Perfect: true`). The SMEM stage's verdict on this tiling is the
conservative contract in action — the bank window (byte bits [2,7)) sees
only the three lane bits and no lane bit exists above it:

```
swizzle error: no free degree
```

(Output reproduced by running the stage pipeline on this problem; see
`example/main.go` for the runnable version.)

## 4. Guarantees the code enforces

Every claim below is backed by a test gate in `internal/f2` (paths relative
to that package); the suite is the oracle.

| Guarantee | Mechanism | Test gate |
|---|---|---|
| **Canonical forms** — every expression folds to a unique normal form via six rules over a structural total order (`Const < Symbol < Variable < Binary`) | rewrite engine (`fold.go`) | `canon_test.go`: all 10,788 expressions up to 4 leaves fold canonically and idempotently |
| **Convergence** — termination (per-rule well-founded witnesses) + confluence (Newman's condition via permuted rule orders) | fixed-order rule driver iterating `rewriteRuleOrder` | `convergence_test.go`: `TestFoldMeasureDecreases`, `TestFoldConfluence` |
| **Linearity** — mappings are permutations (bijective) or guarded stride classes; certification is exact F₂ rank via Gaussian elimination | `matop.go`, `coeff_mat.go` | `layout_cuda_test.go`, `pipeline_test.go` |
| **Coalescing scores are certified against volume floors** — `sectorRank ≥ laneBits + dtypeSize − Sector`, `lineRank ≥ max(0, laneBits + dtypeSize − Line)`; both met ⇒ perfect | `gmem_coalescing_map.go` | `gmem_coalescing_map_test.go` |
| **Swizzle is a bijective involution** — bank slice rank decides saturation; `SwizzleErrorSaturated` is a success (already conflict-free), declines are loud errors | `swizzle_map.go` | `layout_cuda_test.go` |
| **Determinism** — no map iteration anywhere in the fold driver | `fold.go` | whole suite passes under `-count=20` |
| **Lowered ASTs equal native results** — for every assignment on enumerated problems, `ast.Eval(lowered)` equals the native pipeline's byte offset, both algebras, all three stages; offsets stay bijections | `pkg/layout` lowering (`lower.go`) | `pkg/layout` tests (`f2_test.go`, `subgroupchain_test.go`) |

The framework-wide contract is **conservative**: do what you can, return an
`error` when you cannot. False negatives (bailouts) are acceptable; false
positives (wrong math) and silent failures are not.

## 5. Use cases

- **GMEM coalescing.** Derive the permutation M that places lane bits in
  the lowest logical positions and certify the per-warp sector/line score.
  The F₂ pass assumes the trailing-lane hardware convention and certifies;
  mis-ordered coordinate vectors are the sub-group chain's family-swap
  territory.
- **SMEM bank-conflict analysis and swizzle derivation.** Decide whether a
  bank window is saturated (conflict-free as-is), derive the XOR swizzle
  when free lane bits exist above the window, or get a classified decline
  when the layout cannot be repaired within the model.
- **Bijectivity/certification of arbitrary bit permutations.** Rank and
  nullspace of any linear layout map, exact and cheap.

When F₂ is **not** the right tool: non-power-of-2 tiles or pitches
(carries break F₂-linearity), affine/constant offsets (the model is purely
linear; emit integer adds on top), and symbolic-coefficient rank questions
(symbols live in the stride class; bijective cores are constant-coefficient
by design). Reach for [`doc/subgroupchain.md`](./subgroupchain.md) instead.

## 6. Which algebra?

| Your problem | Choose |
|---|---|
| Power-of-2 tile, power-of-2 strides, need exact/certified answers about ranks, sectors, banks, bijectivity | **F₂** (`layout.F2`) |
| Arbitrary tile factorizations (7×16×4, 96-wide rows, …), CuTE-style hierarchical tuples, can accept conservative "cannot optimize" verdicts | **sub-group chain** (`layout.SubgroupChain`) |
| Affine offsets, padding, non-pow2 pitches | neither, today — emit integer arithmetic on top of the linear part and see each algebra's "out of scope" notes |

Both algebras share the same consumer facade (`pkg/layout`), the same
interchange AST (`pkg/ast`), and the same conservative contract, so the
choice is a one-token change once the problem satisfies the chosen
algebra's preconditions.
